# P0.3 — Historical Dependency Recovery Spike

**Branch:** `p0/historical-dependency-recovery-spike`
**Baseline:** `8be421b944934b13324d66e6e629ec2ca73b420c`
**Historical producer:** `665bb1ef13c3eeff2e84bf6e0d588a6bdecc6a92`

**Outcome:** isolated manifest candidate prepared; lockfile generation and installation stopped at supply/provenance gates. No production dependency or lockfile changed.

## Executive result

The exact historical package contracts contain several independent identity and lock problems, not one safe rename:

1. MCP `package.json` declares `@logos/plugin-types`/`@logos/plugin-styles@1.4.1`, while historical MCP source imports `@penpot/*` and its lock already resolves the `@penpot/*@1.4.1` packages.
2. Registry artifacts for those exact `@penpot` versions are available; their downloaded bytes match npm’s published SHA-512 integrity and npm registry signatures verify. However, the registry version records and tarballs do not identify an upstream repository or source commit. Artifact integrity is established; source-to-commit provenance is not.
3. The frontend, plugin-runtime, and MCP workspace identities/imports disagree across manifests, source imports, and lockfiles. The plugin-runtime lock importers omit six declared build dependencies, and the type dependency is not consistently declared.
4. The frontend also pins `svgo` and `draft-js` to codeload tarballs with no lockfile integrity hashes. F06 recorded repeated codeload resets. `svgo`’s commit signature was verified in F07; `draft-js`’s pinned commit is unsigned. Neither archive was downloaded or retried here.
5. A lockfile-only candidate was attempted in a disposable `665bb1ef` worktree with pinned Node and verified pnpm. npm registry access from that container failed through the forwarded loopback proxy before pnpm could update the lock. No frozen install or package code installation was run.

**Stop decision:** no install/build is authorized from this evidence. Ask package owners to attest the `@penpot` source repositories and source commits for versions 1.4.1, and provide an approved registry egress/toolchain path. Separately, obtain verified codeload archive bytes and independent digests (and an owner attestation for unsigned `draft-js`) before attempting the frontend install. Do not use a mirror or alter active lockfiles.

## Build and current-consumer gate

The historical `render-wasm/build` script was inspected, not changed or run. It checks only whether `/opt/emsdk/emsdk_env.sh` exists; if absent it prints a warning and exits `0`, without checking the Emscripten version. Later copy commands would fail for absent source files, but there is no explicit nonempty-artifact/import contract check. The wrapper therefore violates the fail-closed requirement for missing Emscripten. The frontend producer was not run because dependency and toolchain gates are not met.

Current `logos-app` workspace packaging expects generated modules under `logos-app/dist/js`, including `main.js`, `main-workspace.js`, worker/shared modules, and renderer assets. The historical output path is `frontend/target/dist`; no complete produced bundle was available to compare or execute. No browser/runtime evidence is claimed.

## Unverified assumptions and decision requested

- npm registry signatures and tarball digests establish the exact published `@penpot` artifact bytes, but do not identify the Penpot repository commit that produced them. Package maintainer/source-owner attestation is still required before calling this a source-authentic reconciliation.
- Historical source imports may rely on package aliases not represented by the manifests (`@logos` declared vs `@penpot` imported for the plugin runtime, SVGO and Draft.js). Only a successful full Shadow-CLJS build can resolve this question; no alias is assumed.
- The six Vite/TypeScript build dependencies have no resolved importer versions/integrities. Their exact graph cannot be inferred from the ranges or from unrelated lock entries.
- F07’s codeload source commits do not authenticate tarball bytes; `draft-js` also has an unsigned commit. No package/source owner attestation or expected archive digest was provided.
- This spike examined disputed direct edges, not all 219 MCP packages; a complete SBOM, license and transitive provenance audit remains unperformed.

**Decision requested:** package owners should (1) provide canonical source repository + commit attestations for the published Penpot 1.4.1 plugin packages, (2) decide the intended `@logos`/`@penpot` runtime, types, style, SVGO and Draft.js import contracts, (3) attest an independent expected digest for the codeload artifacts (including unsigned `draft-js`), and (4) provide approved registry egress for the pinned isolated toolchain. Until then, keep this as a documented manifest candidate only. Do not perform a frozen install, generate production lockfiles, modify routes, or start the historical build.

**Outcome:** historical dependency recovery remains blocked. The source and exact versions are identifiable, and two npm artifacts’ registry integrity/signatures are verified; source commits for those artifacts, missing frontend dependency resolutions, Git archive bytes, and a working isolated registry path are not. P0.3 must not proceed to a full build until these gates are addressed. M0/M1 remain open.
