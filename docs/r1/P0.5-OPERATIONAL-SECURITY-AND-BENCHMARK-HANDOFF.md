## B5 — Deployment-owner evidence checklist

Before any environment probe, the authorized owner records:

- Environment and deployment identifier; Go image/build SHA; deployment time.
- Ingress/proxy product and configuration revision, or confirmation that Go
  terminates HTTPS directly.
- Effective `BACKEND_GO_WEBSOCKET_ALLOWED_ORIGINS` origins, read through the
  approved runtime configuration interface. Record origin values only; never
  export or attach the process environment.
- Approved browser Origin, including scheme, hostname, and port; test-account
  identity label; disposable team/file IDs; test window and operator.
- Authorization that the named non-production account, team, file, PostgreSQL,
  and Redis instance are disposable and may be used for these tests.

Do not record passwords, cookies, session tokens, database URLs, query strings,
or raw request/response headers. The probe emits only case names, expected and
observed status codes, mode, and pass/fail.

## B5 — Authenticated WebSocket Origin probe

`test/security/deployment/probe_ws_origins.py` uses only Python's standard
library. It performs authenticated WebSocket handshakes against a **non-
production** endpoint; it does not send application messages or mutate files.
The authenticated case expects HTTP 101. Each denied Origin case expects HTTP
403. A 401/422 is a failed run because authentication/session setup was not
valid. All seven outcomes must pass.

Run from the repository root in a private terminal. The cookie read is
non-echoing; shell tracing must remain disabled:

```sh
set +x
export DEPLOYMENT_ENVIRONMENT=nonproduction
export DEPLOYMENT_OWNER_AUTHORIZED=true
read -r -p 'Non-production WSS endpoint (no credentials/query secrets): ' LOGOS_WS_URL
read -r -p 'Authorized HTTPS browser Origin: ' AUTHORIZED_BROWSER_ORIGIN
read -r -s -p 'Short-lived test session cookie (name=value): ' LOGOS_WS_COOKIE
printf '\n'
export LOGOS_WS_URL AUTHORIZED_BROWSER_ORIGIN LOGOS_WS_COOKIE
```

`LOGOS_WS_URL` must be `wss://.../ws/notifications?session-id=<UUID>` and may
contain no other query parameters. `LOGOS_WS_COOKIE` and `AUTHORIZED_BROWSER_ORIGIN`
are held in process environment only; never paste them into a command line,
ticket, or evidence artifact. Use the direct mode only when the public HTTPS
connection terminates in Go. Use reverse-proxy mode only when the public
ingress terminates TLS and the runtime allowlist explicitly contains the
approved HTTPS Origin.

```sh
python3 test/security/deployment/probe_ws_origins.py \
  --mode direct \
  --output /tmp/logos-ws-origin-evidence.json
# Or, for TLS termination at the reverse proxy:
python3 test/security/deployment/probe_ws_origins.py \
  --mode reverse-proxy \
  --output /tmp/logos-ws-origin-evidence.json
```

The seven cases are: authorized Origin; missing Origin; malformed Origin;
opaque `null`; unauthorized host; scheme mismatch; port mismatch. The script
requires an owner-authorized non-production run, validates direct-mode
host/port identity, uses normal TLS certificate verification, and records no
URL, cookie, or Origin string. Its JSON file is mode `0600`. Protect and retain
that file only in the approved non-production evidence store. After the
selected probe, clear the variables:

```sh
unset LOGOS_WS_COOKIE LOGOS_WS_URL AUTHORIZED_BROWSER_ORIGIN
unset DEPLOYMENT_ENVIRONMENT DEPLOYMENT_OWNER_AUTHORIZED
```

### Direct HTTPS to Go

The allowed browser Origin must match the public WSS host and port. The Go
process must see TLS (`r.TLS != nil`) and the matching `Host`. Verify the live
direct endpoint, then compare the status-only report with the Go build SHA.
Same-origin HTTPS does not require a cross-origin allowlist entry; all other
Origins must fail.

### HTTPS through reverse proxy

First verify the effective runtime allowlist contains the exact approved
browser origin. The proxy must preserve the browser's `Origin` and expected
`Host`; authorization must not depend on `X-Forwarded-Proto`. The Go process
terminates plain HTTP behind the proxy, so the allowlisted HTTPS origin is what
authorizes the browser upgrade. Run the probe through the public non-production
ingress, not directly to the upstream service.

### Resource authorization, revocation, cleanup, and stale history

The script above tests handshake Origins only. Run the existing production-router
integration suite against a fresh loopback-only PostgreSQL database and a
disposable loopback Redis service for team/file authorization, permission
revocation, delivery suppression, disconnect cleanup, and stale-history
non-mutation. The wrapper accepts only URL schemes `postgres`/`postgresql` and
`redis`/`rediss`; it accepts the literal hostname `localhost` or an IP address
in the loopback range, and requires a PostgreSQL database name beginning with
`logos_p04`. These are early rejection guards only. They do not prove that the
database or Redis instance is disposable, isolated, owned by the operator, or
safe to mutate. In particular, the check does not resolve `localhost`, inspect
port forwarding or proxies, inspect container boundaries, or identify other
clients sharing the service. `TEST_REDIS_DISPOSABLE=true` is an operator
confirmation flag, not evidence of isolation. The initializer also checks the
target PostgreSQL schema is empty before migrations; that check does not prove
that the database itself is isolated or replaceable.

Before setting the confirmation variables, the deployment owner must
independently verify the selected account, service identities, network and
container boundaries, database and Redis contents, and that no shared or
production resources can be reached. If those facts cannot be established,
do not run the initializer or integration suite.

Start fresh disposable services yourself, then set their URLs in a shell that
does not echo commands or environment values:

```sh
set +x
export DEPLOYMENT_ENVIRONMENT=nonproduction
export DEPLOYMENT_OWNER_AUTHORIZED=true
read -r -s -p 'Fresh loopback PostgreSQL test URL: ' TEST_DATABASE_URL
printf '\n'
read -r -s -p 'Disposable loopback Redis test URL: ' TEST_REDIS_URL
printf '\n'
export TEST_DATABASE_URL TEST_REDIS_URL
export TEST_REDIS_DISPOSABLE=true
bash test/security/deployment/run_disposable_security_tests.sh
unset TEST_DATABASE_URL TEST_REDIS_URL TEST_REDIS_DISPOSABLE DEPLOYMENT_ENVIRONMENT DEPLOYMENT_OWNER_AUTHORIZED
```

The tests exercise anonymous/missing-Origin/cross-Origin rejection; authenticated
same-origin and allowlisted upgrades; allowed and denied team/file operations;
delivery after authorization revocation; unsubscribe/disconnect cleanup; and
stale-history 409 rejection without file revision or change-row mutation. They
do not exercise the public production ingress. Retain only sanitized `go test`
pass/fail output, test-run ID, test build SHA, and disposable-service identity.

## B6 — Future approved editor-runtime memory job

### Current contract status

Readiness v2 separates `infrastructure`, `heap_capture_capability`, and
`benchmark_execution`. Infrastructure success is not a heap capability;
successful CDP snapshot collection is not a benchmark result. The execution
state remains **NOT_MEASURED** until a real job completes and emits a validated
result.

The generated fixture's 10,000 Go change-history rows are operation history,
not 10,000 rendered shapes. Derive shape count from the selected page's decoded
document structure and verify it against the actual canvas output.

The import gate requires `BENCHMARK_DISPOSABLE_ENVIRONMENT=true`, a valid
project UUID, and matching `BENCHMARK_DISPOSABLE_CONFIRMATION`. These strings
are a guard against accidental import, not proof that the destination is
disposable. An authorized owner must independently attest the account, project,
database, and environment isolation. The hosted readiness workflow provides
none of these values and performs no import.

The old `globalThis.logosBenchmarkEvidence.collect()` response contained
caller-supplied metadata; matching `fileId`, page count, canvas dimensions, or
hash fields alone did not prove file load or visible rendering. The preflight
now fails closed after navigation: it does not accept page-global metadata and
does not run CDP heap capture without independently verifiable loaded-file and
canvas evidence. This work does not create that editor integration. Browser
readiness and heap-capture capability remain **BLOCKED**.

### Required measurement-job contract

An explicitly approved integration with the actual editor runtime must:

1. Provision and attest a disposable environment, account, project, and test
   file. Import the fixture only there. Record the fixture archive SHA-256 and
   selected page's decoded object count; never equate change rows with shapes.
2. Observe the successful authenticated `get-file` response for the exact
   imported file and verify its returned file ID. Independently verify the
   editor document store is displaying that same file and selected page. A URL,
   DOM attribute, or test-only metadata object by itself is insufficient.
3. Capture the actual Rust/canvas renderer output through a browser screenshot
   of the visible canvas. Decode pixels and assert fixture-derived occupied
   and background pixels (with documented tolerance), canvas dimensions, and
   page controls. Record the renderer build and path (Rust/WASM/WebGL or other
   approved path); fail if fallback or unsupported mode is active. Do not count
   DOM shape nodes as renderer evidence.
4. Pin browser name/version, OS/image, architecture, renderer build, app build
   SHA, fixture SHA, page ID, imported file ID, and measurement harness SHA.
   Record all values in the JSON result.
5. Load a fixed page and wait for renderer idle. Warm up with a versioned,
   deterministic interaction sequence, force GC, capture a baseline heap
   snapshot, run the same sequence, force GC, and capture the final snapshot.
   The sequence must include at least one reproducible selection/edit/undo or
   equivalent documented operation on a known fixture shape, then restore the
   document. Record durations and iteration counts; do not save into shared
   projects.
6. Analyze baseline/final snapshots using pinned tooling and report retained
   JavaScript heap growth, detached DOM nodes, and ArrayBuffer growth separately.
   Keep WASM linear memory, GPU allocations, and backend RSS separate; a JS heap
   snapshot does not measure them. Thresholds must be approved and versioned
   before the run. No thresholds or metrics are asserted by this handoff.
7. Produce a machine-readable result with execution status `PASSED`, `FAILED`,
   or `BLOCKED`, exact build/run identities, fixture and browser metadata,
   interaction log, snapshot-analysis summary, and artifact checksums. Retain
   baseline/final snapshots, canvas screenshot/pixel-check report, JSON result,
   and sanitized browser/runner logs. Exclude cookies, credentials, user data,
   and raw environment dumps.

Missing/empty reports, missing snapshots, report-generation errors, unsupported
browsers/renderers, absent loaded-file proof, or unsuccessful execution must
be **BLOCKED** or **FAILED** and must never produce `PASSED`. Missing required
artifacts fail the job. A passing measurement is separate from infrastructure
and heap-capture readiness. Until this job exists and runs successfully,
performance remains **NOT MEASURED**.
