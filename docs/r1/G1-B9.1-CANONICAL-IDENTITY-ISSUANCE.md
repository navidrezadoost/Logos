# G1-B9.1 — Canonical Identity Issuance and Legacy Compatibility

Status: implementation and qualification evidence for the identity lifecycle. This does not authorize Rust production mutation authority.

## Ownership and issuance inventory

| Record / lifecycle | Issuer and boundary | Durable representation | Compatibility contract |
| --- | --- | --- | --- |
| Server document | Go `insertFileInTx`: accepts a client file ID if supplied, otherwise generates a UUID; `create-file`/`create-project` returns the persisted ID. React associates identity only after `get-file` returns the exact requested ID and page order matching the hydrated document. | Go file row and returned ID. React's offline snapshot records the ID and `server` provenance after verification. | Existing Go create-file acceptance behavior is unchanged. A route parameter or IndexedDB key alone is not proof of server ownership. |
| Server page | Go `filedata.NewPageID()` creates a UUID while seeding the file; the create response includes the persisted page ID. | Serialized Go file data and `CreatedFile.Pages`. | No page ID is regenerated during React hydration. |
| Offline document | `createOfflineDocument()` in `logos-app/src/offline/persist.ts` allocates one UUID at the offline creation boundary and writes the initial IndexedDB snapshot before resolving. Callers must await it before enabling edits. | `snapshots` record key and record `documentId`, plus matching snapshot identity and `offline` provenance. | There is no production offline-creation UI today. The API rejects attaching a new ID to an already populated/identified document. Retry returns the existing offline identity. |
| Initial React page / added page | React document store uses `crypto.randomUUID()` for its initial empty page and `addPage()`. | In-memory page graph; offline snapshots persist it, server persistence follows existing editor behavior. | Existing hydrated page IDs remain byte-for-byte unchanged, including historical nanoid IDs. |
| Shapes / ordinary edits | Existing document records retain their supplied IDs. Current editor-created shapes use `crypto.randomUUID()`. | Document snapshot / existing persistence boundary. | Editing preserves identity. This milestone does not repair imported or historical IDs. |
| Duplicated template subtree | `templateStore` allocates fresh IDs for copied shapes and rewrites relationships within the copied graph. | Added through document-store compatibility operations. | Duplication IDs are new; source IDs remain on the original records. External source aliases are not a general document identity registry. |
| XD / Sketch import | Converters allocate fresh UUIDs and use per-conversion maps for source node relationships (Sketch `do_objectID`; XD node/symbol IDs). | Resulting imported shapes/pages use converted IDs. | Source maps are conversion-local and are not persisted as source aliases. Cross-import deduplication/source identity preservation is incomplete and intentionally not inferred. |
| Rust renderer synthetic root | Renderer projection only. | Not persisted by the document store. | Never treated as a user document/page/shape identity. |

`logos-app/src/api/client.ts` resolves a project to a server file and reads it with `getFile`; its current file/page resolution does not alter server identifiers. Go `BuildEmptyData` is passed the page ID generated by the file creation transaction, so the response and serialized document share that ID.

## Identity and compatibility contract

1. A server document identity is canonical only when the authenticated response ID exactly equals the requested file ID, is a UUID, and its ordered page IDs exactly match the hydrated React document. The existing Go endpoint may continue accepting client-provided IDs; this work does not change that API contract.
2. An offline document identity is canonical only after the UUID and initial snapshot have been written under the same IndexedDB document key. New edits must wait for `createOfflineDocument()` to resolve.
3. New pages use UUIDs. Hydration, renderer synchronization, retries, shadow evaluation, import, and page switching never issue replacement IDs.
4. Existing document, page, and shape IDs are immutable compatibility data. In particular, historical nanoid pages and imported identities are not rewritten to improve Rust eligibility.
5. Shape duplication creates fresh shape IDs once and remaps relationships internal to the duplicate. It does not change original IDs or infer cross-import aliases.
6. Pre-contract IndexedDB snapshots have no trustworthy embedded identity provenance. They load without ID repair and are marked `legacy` until the exact server file is verified. A missing or mismatched outer document key prevents hydration.

## Rust candidate eligibility

`classifyRustIdentityEligibility()` is a pure read-only check over the current identity metadata and the existing React-to-Rust candidate adapter. Its result is one of:

| Result | Meaning |
| --- | --- |
| `CANONICAL_UUID_READY` | Server or offline identity has trusted provenance and the complete current snapshot passes the existing adapter conversion contract. This is candidate readiness only, not Rust authority. |
| `LEGACY_IDENTITY` | Legacy provenance or a noncanonical document/page/shape ID prevents conversion. IDs remain unchanged. |
| `DOCUMENT_ID_UNAVAILABLE` | No document ID is bound. |
| `UNSUPPORTED_DOCUMENT_CONTENT` | Identity is available but the adapter rejects document content, shape types, properties, fills, geometry, or structure. Vector Networks, components, and other unsupported records remain on the React compatibility path. |
| `AMBIGUOUS_OWNERSHIP` | An ID exists without verified server/offline provenance, or provenance is inconsistent. |

The classifier does not call Rust, write IndexedDB, mutate Zustand, normalize differences, or synthesize IDs. `CANONICAL_UUID_READY` remains restricted by the existing one-page adapter and its lossless subset. It does not establish round-trip compatibility for arbitrary documents or authorize production Rust commits.

## Persistence and hydration boundaries

- New offline snapshots store matching outer key, record ID, inner snapshot ID, and `offline` provenance.
- Reload checks the outer record ID against the requested key before hydration.
- New-format server provenance is restored only for a matching UUID. Existing snapshots lacking embedded provenance are treated as legacy; a verified `get-file` response may then associate the exact server ID.
- Eligibility reads are pure; they do not alter `savedAt` or write snapshots.
- `WorkspacePage` clears stale in-memory ownership on document switch, restores cached state if present, then attempts exact server-ID and page-order verification. A missing cache, failed request, or page mismatch leaves the document on its compatibility path. There is no production Go-to-React document hydration adapter today, so cold server workspaces do not gain canonical identity through this milestone.

## G1-B9.1 verification evidence

The P0.5 disposable Chromium proof covers exact server ID/page association, UUID page issuance, historical page ID preservation/editing, all five eligibility classifications, unsupported content rejection, and classifier non-mutation. A separate Node test suite uses `fake-indexeddb` to exercise offline creation-before-edit persistence, server/offline identity reload stability, and read-only eligibility without Chromium's `--virtual-time-budget` scheduler. The existing P0.5 Chromium portion still uses the workflow's disposable PostgreSQL fixture and requires no production database or credentials.

Known limits: there is no user-facing offline document creation flow; imported source aliases are not persisted; adapter support remains intentionally limited; this milestone makes no claim of production Rust authority or broad document eligibility.
