# P0.5 Track E — Runtime Security and Revision Contracts

**Base:** `f309baa72fbcd66c81f9215e91d4e4e05461f846`
**Scope:** Go WebSocket Origin/resource authorization and fail-closed stale-revision history handling. No route, schema, cookie format, persisted document, or renderer change is made.

## Implemented contracts

### WebSocket Origin and resource access

- `wsCheckOrigin` rejects malformed/opaque origins, cross-host/cross-port origins, and scheme mismatches. It never trusts `X-Forwarded-Proto`; direct TLS uses `r.TLS`. TLS-terminating proxy deployments must configure exact browser origins in `BACKEND_GO_WEBSOCKET_ALLOWED_ORIGINS`, parsed into `server.Deps.WebSocketAllowedOrigins`. Unit and router integration tests verify the explicit allowlist path. Requests without `Origin` remain allowed for legacy non-browser clients; browser clients still send an Origin.
- The WebSocket handler receives the existing database pool. `subscribe-file` and `subscribe-team` require `CanRead` from the existing file/team permission queries. Query errors, missing pools, and absent memberships deny access.
- `pointer-update` requires file read access. Resource notifications are reauthorized immediately before forwarding; a denied event is dropped, and a directly matching subscription is revoked.
- File and team topics share a raw UUID namespace. Messages are classified by event payload before authorization (`library-change` as team; file events by their `file-id`/`fileId`) so an ID collision cannot inherit authorization from the other resource kind. Unclassified resource-channel messages are dropped.
- Ping control frames use Gorilla's concurrent-safe control-write API. The WebSocket route remains legacy-compatible; this PR does not enable it for production editor traffic.

### Revision-history integrity

- Stale `update-file` requests require every revision in `(baseRevn, currentRevn]` to exist in order and decode as a JSON change array with nonempty operation types.
- Missing revisions, null/empty/malformed data, and legacy Transit+zstd bytes return a typed `CompetingChangeHistoryError`; the endpoint responds `409 change-history-unavailable` before applying or committing the stale request.
- The existing best-effort `loadLaggedChanges` response path is not upgraded to a complete history-decoding contract by this change; malformed post-commit lagged payload behavior remains a separate follow-up. This is not evidence that legacy collaboration history is fully compatible.

## Disposable integration coverage added

`notifications_ws_integration_test.go` exercises the production `server.New` route and middleware with a real WebSocket client, PostgreSQL session/permission rows, and Redis Pub/Sub. It covers unauthenticated and cross-Origin upgrades, permitted team/file subscriptions and delivery, cross-team team/file rejection, permission revocation with dropped events and subscription cleanup, reconnect authorization, and cleanup after disconnect. `files_update_integration_test.go` seeds a legacy Transit+zstd marker as competing revision history and asserts the stale update returns 409 without changing the file revision or adding a change row.

These integration tests passed locally against fresh loopback-only PostgreSQL and Redis containers with no volumes or user data (Postgres image digest `postgres@sha256:16bc17c64a573ef34162af9298258d1aec548232985b33ed7b1eac33ba35c229`; Redis digest `redis@sha256:bb142a9c18ac18a16713c1491d779697b4e107c22a97266616099d288237ef47`). ```sh


The ordinary `go test ./...` run without database URLs skips the PostgreSQL/Redis integration cases. Unit tests cover Origin cases (including scheme/proxy cases), missing permission backend, event/resource-kind classification, malformed history errors, and accepted JSON arrays. The new live integration tests have passed locally but have not yet passed hosted CI.

Therefore the contracts are **partially implemented, not security acceptance**. Before enabling real editor traffic, run the new disposable-PostgreSQL/Redis tests in hosted CI and configure/test the deployment's exact proxy-origin allowlist. Decide whether missing-Origin clients remain allowed. The reconnect test reuses the valid session after permission revocation; session expiry/revocation itself is not covered. The tests verify Redis unsubscribe after disconnect, while goroutine termination is supported by source-level lifecycle checks rather than a direct goroutine-leak assertion. The historical candidate schema remains provisional.
