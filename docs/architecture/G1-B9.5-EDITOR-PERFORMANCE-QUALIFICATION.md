# G1-B9.5 Editor Performance Qualification

**Status:** NOT MEASURED (awaiting a successful hosted Chromium run on the final PR head)

**Scope:** Non-production qualification of the production React editor and its existing Rust/WASM renderer.

**Baseline:** `0d643e3bf0eadcc8e921d000f702e488bff70ae8`

## Measurement boundary

The harness mounts the production `Toolbar`, `LayersPanel`, `Canvas`, and `Inspector`. Playwright clicks test controls that call the existing `useDocumentStore.applyHierarchyOperation`; the production `Canvas` then observes the Zustand state and follows its normal scene projection and Rust/WASM upload/render path. Fixtures are hydrated in memory and are never saved or sent to the backend. The benchmark does not enable shadow authority or change the document contract.

The measured React path records page-scoped hierarchy planning and validation, Zustand publication wall time (including its synchronous subscribers), and selection reconciliation. Selection reconciliation is a nested part of publication and must not be added to publication when computing totals. The renderer reports scene projection/capability validation, WASM scene upload, native renderer execution, total synchronous scene path, browser scheduling to the next animation frame, and the renderer WASM heap reservation. Rust candidate conformance is measured separately before each measured user interaction: React planning, React-to-Rust conversion, Rust evaluation and JSON parsing, and Rust-to-React projection. Candidate timings are diagnostic comparisons, not production edit-path timings.

The user-facing interaction-to-frame value starts at the browser click event timestamp and ends after the renderer reports a later frame, a further animation-frame boundary has passed, and the rendered framebuffer has been checked. Pixel readback is a functional validation step and is outside that reported endpoint timestamp. This endpoint is intentionally defined by observable canvas output, rather than a React commit alone.

## Deterministic workloads and checks

Each fresh in-memory fixture has exactly 21, 85, or 341 shape records and maximum hierarchy depth 3, 4, or 5 respectively. Level counts are `[2, 8, 11]`, `[2, 8, 32, 43]`, and `[2, 8, 32, 128, 171]`; root and child membership is ordered and parent/child symmetry is checked by unit tests. The records consist of nested Frames/Groups and Rectangles. The 10,000 Go change-history rows in the separate readiness fixture are not rendered shapes and are not part of these workloads.

The seven actual production-store operations are root creation, child insertion, rename, sibling reorder, root reorder, subtree deletion, and reparent. Before and after every operation the runner validates the resulting semantic state, selection cleanup where applicable, a later renderer frame, and relevant pixel samples from the production canvas. Reorder operations must change the deliberately overlapping red/orange/blue pixels; creation and insertion must produce the expected green/magenta samples. Rust candidate semantics must agree with the React proposal for every operation. Any mismatch, fallback renderer, missing frame evidence, changed browser pixels, or page error fails the job.

Every browser round contains at least five warm-up interactions and thirty measured interactions per size/operation pair. There are at least two independent headless Chromium launches. Raw samples are retained. The runner summarizes every metric by workload and operation with sample count, p50, p95, maximum, and mean. The first measured round also saves one screenshot per workload/operation. The evidence JSON includes Chromium version and user agent, OS/kernel, CPU model and logical core count, viewport, device pixel ratio, WebGL version/vendor/renderer, fixture definition, functional pixel samples, Rust candidate timings, renderer timings, and available JS/WASM heap observations.

## Interpretation and limitations

This milestone establishes reproducible evidence and stage attribution; no performance target or passing latency threshold has been authorized. A successful run means the specified workflows completed and emitted valid observations, not that an interactive performance SLO has been met. Do not characterize JS heap observations or WASM reserved heap capacity as retained-memory growth or a memory benchmark. Retained growth remains **NOT MEASURED**. Overall performance remains **NOT MEASURED** until the complete hosted run succeeds on the final PR head and its raw artifact is inspected.

The workload is synthetic and intentionally focused on hierarchy operations and the production canvas. It does not claim coverage of text/image effects, large vector networks, collaboration, backend persistence, or arbitrary user documents. CI runner and software/browser versions are part of each evidence artifact and limit cross-run comparison. GPU execution is intentionally disabled in favor of WebGL2/SwiftShader for repeatability; these observations do not represent hardware GPU latency.

The test-build-only stage probe is enabled solely by the dedicated Vite configuration. Normal production builds compile the probe off. It emits no telemetry and does not persist measurements. The benchmark fails closed if the actual production Canvas does not expose the WASM backend.

## Readiness contract

Infrastructure readiness, heap-capture capability, and benchmark execution are separate states. A configured or ready environment is not proof of heap-capture support. A successful heap capture is not proof that a benchmark ran. For the future memory job, success requires a fresh run manifest, supported browser, successful application import and actual pixel evidence, an executed workload, and a complete nonempty report plus raw artifacts. Missing reports, unsuccessful execution, unsupported browsers, or metadata without observed pixels must remain blocked/failed and cannot be interpreted as a passing performance result. Import safeguards must require an independent deployment-owner confirmation that the selected test resources are isolated and authorized; loopback, database-name prefixes, and environment flags alone do not establish that an environment is disposable.

## Future editor-runtime memory job integration

The memory job should use the same pinned Chromium/browser context and deterministic workload definitions, but run in a separately authorized disposable environment. Its manifest must bind the commit SHA, fixture/workload hash, browser and OS versions, viewport/DPR, renderer/backend identity, run ID, and every artifact checksum. The job must perform a fixed interaction sequence after warmup (create, insert, edit, reorder, reparent, delete, repeat) and verify state plus observed canvas pixels before and after each phase.

Capture baseline and post-warmup heap snapshots at named checkpoints, retain the raw snapshots, and report retained growth as post-warmup retained bytes minus the baseline under an explicitly stated GC/capture policy. Include multiple repetitions and distributions rather than a single delta. Record renderer WASM heap capacity separately from browser JS heap and retained object growth. Each capture must identify whether browser GC was exposed and invoked; if it was unavailable, state that limitation and do not claim post-GC retained size. Require complete metadata, logs, report, snapshots, screenshots/pixel evidence, and checksums. Any missing artifact, failed import, unsupported browser, failed operation, non-WASM fallback, absent output, or mismatch between fresh manifest and report must result in failure/blocked status, never a zero-valued pass.
