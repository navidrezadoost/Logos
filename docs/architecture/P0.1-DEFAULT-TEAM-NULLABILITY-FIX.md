# P0.1 — Nullable `default_team_id` Behavior

**Status:** Minimal Go fix and focused regression coverage; schema remains uncertified
**Base:** `0a9a2412653e127ff5aa9a63a6475a0b6bb4ff50` (after PR #56)
**Scope:** `get-teams` / `get-team` read behavior only; no schema or default assignment changes.

## Contract finding

`default_team_id` is **not a universally non-NULL schema invariant**:

- Historical migration `backend/src/app/migrations/sql/0100-mod-profile-indexes.sql` adds `default_team_id uuid NULL REFERENCES team(id) ON DELETE SET NULL`. It populates the value only for profiles matching an owned default team and default project; rows not matching that join remain null.
- Historical Clojure `get-teams` reads `(:default-team-id profile)` and binds it directly to `(t.id = ?)`. A SQL NULL comparison yields NULL (no team is marked default) and does not attempt to cast an empty string to UUID.
- Current Go `Profile.DefaultTeamID` is `*string`. Password registration sets default team/project IDs in its creation transaction, but `CreateTeamHandler` does not. Historical/migrated or incomplete profiles can have no default. The field and old query therefore cannot safely be treated as always present.
- Current Go `GetTeamsHandler` and `getTeam` scanned the nullable column into a plain `string`, ignored scan errors, then passed `""` to a UUID comparison. PostgreSQL returned `invalid input syntax for type uuid: ""` for a valid profile without a default.

## Fix

Use `pgtype.UUID` to retain SQL NULL through the Go query parameter. Both team-list and single-team queries use `COALESCE(t.id = $1, false)` so an absent default produces a false marker, while an actual configured UUID still marks the matching team. A missing profile row leaves the default UUID invalid and is handled as no default. No fake UUID or database default is introduced.

## Verification

The added integration assertions run only when `TEST_DATABASE_URL` points to a disposable database. On the isolated PostgreSQL 16.14 historical-candidate schema (151 historical migration steps plus the current additive Go migration 0001):

- `TestGetTeamsHandler_Integration` — passes for a profile with `default_team_id IS NULL`; its team is returned and not marked default. The same test assigns that team as the default and confirms it is marked true.
- `TestGetTeamHandler_IntegrationWithNullDefaultTeam` — passes and returns the team for a profile with NULL default ID.
- `go test ./...` without `TEST_DATABASE_URL` — passes (database tests skip).
- Full DB-enabled `go test ./...` did **not** complete: the existing `TestUpdateProfileRoundTrip` hangs at test cleanup while `pgxpool.Close` waits. Its cleanup calls `QueryRow` for an `UPDATE` without scanning/closing the row. The focused null-default tests themselves pass. Do not report the full DB-enabled suite as green.

The disposable database used the historical candidate migration lineage; that lineage is not certified canonical. No production or user database was accessed, and this change does not authorize migration use outside a fresh disposable test environment.

## Remaining gate

Keep the fix separately reviewable. The schema owner must still confirm supported nullability and deployed lineage. The full database integration harness needs a separate cleanup fix; schema upgrade/rollback, external object-store lifecycle, and browser/editor verification remain open. This regression closes only the observed empty-UUID behavior, not schema provenance or M0/M1.
