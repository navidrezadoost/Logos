# A10.1 — Structural Mutation Boundary

**Status:** implementation contract and repository audit; compatibility is not a claim that every legacy shape is renderer-supported.  
**Scope:** React/Zustand document-store hierarchy state (`Page.rootShapeIds`, `Shape.parentId`, `Shape.children`, shape-record membership, active page, and selection).

## Boundary and commit rule

Interactive hierarchy edits are planned by `stores/hierarchyOperations.ts` against one captured document snapshot. The planner clones the current-page records, applies an operation to a proposed graph, then asks `buildSceneProjection` to validate reachability, root/child symmetry, ownership and ordering before returning replacement `pages` and `shapes` maps. `documentStore.ts` performs one Zustand commit only for a successful plan. Selection is reconciled from the resulting active-page scene by the document-store subscription; replacement operations select the replacement when the old selection included a removed record. Renderer synchronization observes the committed document-store state through the existing Canvas path.

The compatibility variants (`compat-*`) use this same planner and final graph validation. They retain legacy record types and unknown fields, but return/report a renderer limitation when A9 cannot render the content. They are deliberately not accepted by `applyHierarchyOperation`; callers must use the separately named compatibility API. The compatibility variants are React-side bridge policy, not a second document model. The planned Rust delegation point remains the existing document-core boundary once its compatibility contract is approved.

Rejected operations do not call Zustand `set`, do not mutate the existing maps, and do not change selection. Hydration is separate: `hydrateDocument` validates all pages and graph membership, then replaces the document in one set; it preserves IDs, order and unknown data and rejects malformed/unowned records without repairing them. Renderer-unsupported but structurally valid shapes may hydrate and remain explicitly renderer-limited.

## Structural write-path inventory and disposition

|---|---|---|
| `applyHierarchyOperation`: Canvas root creation; Layers rename, child insert, reorder and reparent; `addRect`; `reorderPageShapes`; strict `removeShape` | **A — supported validated operation** | Strict A10 operations only. Full candidate graph and operation invariants validate before atomic commit. Unsupported A9 render capabilities reject on this path. |
| `addShape`: Canvas ellipse/path/freehand compatibility shapes; AI generation/edit flows; plugins; templates; older editor callers | **B — legacy compatibility operation** | Rectangles and frames use strict create/insert when supported. Renderer-limited or legacy types use `compat-add-shape`. Empty incoming child membership is required; parent must be on the active page; both parent/child links are constructed in the proposal. Unknown fields and visual properties are preserved. Render limitations are returned to the caller or logged; no visual field is silently filtered. |
| `addShapes`: template insertion | **B — legacy compatibility operation** | Related cloned shapes validate as one batch, including parent references independent of input order; one invalid member rejects the complete batch. The existing template ID remap remains its import behavior. |
| `addVectorNetwork` | **B — legacy compatibility operation** | Geometry indices/points validate before planning. The vector is added through `compat-add-shape`, preserving its geometry and visual data, with graph checks before commit. |
| `replaceWithVectorNetwork` (Toolbar boolean operation) | **B — legacy compatibility operation** | Every selected ID must have one owner on the active page; targets must be vector networks with the same parent and no descendants; locked targets/parent reject. Replacement preserves root/sibling position, removes only the selected records, validates once, and reconciles selection. No partial remove occurs. |
| `removeShape` | **A — supported validated operation**, with **B** fallback | Uses strict subtree delete first. Only an A9 renderer limitation allows the explicit compatibility delete fallback. The entire referenced subtree and its external parent are checked for locks; graph validation then confirms all links and membership are removed consistently. |
| `promoteToComponent` | **B — legacy compatibility operation** | One uniquely page-owned Frame/Group is promoted through the planner. Its hierarchy and metadata are preserved; the component renderer limitation is surfaced. Other types and ambiguous ownership reject/return null. |
| `addInstanceShape` (AssetsPanel; Canvas component drop) | **B — legacy compatibility operation** | Adds one instance shell via the planner. Callers undo the component-store instance record if document insertion rejects. The instance remains structurally valid and explicitly outside the verified renderer contract. |
| `updateShape`, `batchUpdate`: Inspector values, AI value edits, offline server value sync, plugin patching | **C — structural fields rejected; nonstructural compatibility updates retained** | `id`, `parentId` and `children` patches reject with `LOGOS_OPERATION_USE_HIERARCHY_BOUNDARY`. Batch patches preflight all IDs and all structural keys before a single record-map update. These APIs remain for non-membership values; they are not hierarchy operations. |
| `addPage`, `setCurrentPage` | **A — page-membership boundary** | `addPage` adds an empty page and page-order entry atomically. `setCurrentPage` accepts only an existing page; page switching clears selection through the existing subscription. They do not move shapes between pages. |
| `hydrateDocument` / IndexedDB `loadPersistedDocument` | **D — atomic hydration** | Validates page index, exact page/record keys, ownership, reachability and graph projection before commit. Invalid snapshots remain stored and are reported; no IDs or malformed structures are rewritten. Renderer-unsupported shapes are preserved with a rendering limitation. |
| Sketch/XD conversion and document-core React adapter | **D — conversion proposal only** | These modules construct/validate conversion snapshots and do not write the live Zustand store. Any future application of converted documents must use `hydrateDocument` (or a separately approved atomic import boundary), never replay partial per-shape writes. |
| `useDocumentStore.setState` in app source | **C — unsupported direct write** | Audit found no production application call to the document store's raw `setState`. Test-only malformed-state fixtures deliberately use it to prove rejection behavior. Document-store structural `set` calls are limited to successful planner commits and validated hydration. Test-only writes are not an application API. |

## Action and call-site notes

- `Canvas.tsx`: rectangle/frame creation already uses the strict hierarchy operation. Ellipse/path compatibility creation calls `addShape`. Pen completion calls `addVectorNetwork`. The line/arrow naming update patches only `name`; it no longer reinserts a duplicate ID. Component drop rolls back component-store registration if the document insert fails.
- `Toolbar.tsx`: boolean vector replacement calls `replaceWithVectorNetwork`.
- `LayersPanel.tsx`: rename/reorder/child insertion call strict `applyHierarchyOperation`.
- `Inspector.tsx`, AI value edits, offline sync and plugin patch API use `updateShape`/`batchUpdate`; structural keys are blocked. Plugin fill conversion still has its documented solid-fill capability limit, but that is separate from structural membership.
- `AssetsPanel.tsx` and component drop create one instance through `addInstanceShape`; rejected document insertion removes the just-created component-store instance metadata.
- `templateStore.ts` is the only discovered multi-shape live insert flow and now uses atomic `addShapes` rather than a sequence of independently committed `addShape` calls.
- `aiStore.ts`: generated multi-shape prompt templates and breakpoint copies collect their records first and use `addShapes` for one all-or-nothing compatibility commit; single generated shapes still use `addShape`. AI style/value updates remain nonstructural.
- Test harnesses that initialize document state use `hydrateDocument`; direct raw store mutation remains only in negative tests that deliberately inject malformed state.

## Validation and renderer policy

Strict operations require A9 projection and capability validation to pass. Compatibility operations still require a valid complete graph, but allow renderer diagnostics `LOGOS_SCENE_UNSUPPORTED_SHAPE` and `LOGOS_SCENE_UNSUPPORTED_CAPABILITY`; the candidate result carries that diagnostic. Store call sites report the limitation, and Canvas retains its ordinary renderer diagnostics/recovery path. This policy preserves data while distinguishing “structurally accepted” from “currently rendered.” It does not assert that unsupported shapes will be visible.

The hierarchy boundary checks page ownership before page-scoped plans. Shape IDs are globally keyed; duplicate canonical IDs and records reachable from multiple pages are rejected. Replacement and add operations reject cross-page ambiguity. Hydration rejects any unowned record because this model has no independent `shape.pageId` field from which to infer ownership.

## Test evidence required for this contract

`test/a10/hierarchy-operations.test.mjs` exercises strict operation invariants, malformed graph rejection, selection reconciliation, compatibility adds/deletes, vector creation and multi-replacement order, descendant rejection, hydration preservation/rejection, atomic batch compatibility insertion, and cross-page replacement rejection. `test/benchmarks/a10-editor-interactions-smoke.mjs` retains the A10 Chromium interaction suite and adds visible renderer-limitation/data-preservation and multi-vector replacement checks. Existing A8/A9/A10 workflows remain enabled and unchanged; the A10 workflow trigger includes the changed store, test-support and test paths.

## Explicit limitations

- This boundary is a React compatibility boundary, not canonical Rust document promotion.
- Renderer support for legacy ellipse/path/component/instance/vector content remains limited by the verified A9 contract. Records and fields are retained; successful rendering is not promised by compatibility insertion.
- React's structural validation remains temporary until the approved Rust document-core operation interface can own these exact semantics without lossy conversion.
- The schema and saved-file formats are unchanged. A malformed historical document is rejected at hydration and requires a separately authorized migration/repair tool; it is never silently repaired here.
