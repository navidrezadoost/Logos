# G1-B6.1: Snapshot status and recovery-point usability

## Snapshot status contract

`get-file-snapshots` reports one of these `restoreStatus` values for each
visible snapshot:

- `verified`: a supported SHA-256 envelope matches the stored bytes.
- `legacy-unverified`: non-empty bytes exist without an integrity envelope.
- `unavailable`: bytes are missing or empty.
- `corrupt`: integrity metadata is malformed, uses an unsupported envelope or
  algorithm, or does not match the bytes.

Listing handles verification errors explicitly and maps them to `unavailable`
or `corrupt`; it never omits a failed status or presents it as verified. The
restore endpoint continues to reject unavailable and corrupt content. A
malformed JSON metadata value cannot be stored in PostgreSQL `jsonb`, so the
pure Go verification tests cover malformed JSON directly, while the database
integration tests cover malformed envelopes, unsupported versions, mismatched
digests, and missing content through the API.

## Recovery point retrieval and expiry

The legacy snapshot implementation treats `deleted_at` on system snapshots as
a logical expiry: an unexpired timestamp at or after the current time remains
visible and restorable. G1-B6 had written a 48-hour future timestamp to the
pre-restore `file_change` row, but the Go list and restore paths required
`deleted_at IS NULL`; the row was therefore inaccessible immediately.

The Go paths now follow the established convention for `created_by='system'`:

- A system snapshot with `deleted_at IS NULL` or `deleted_at >= now()` can be
  listed and restored.
- User snapshots remain eligible only when `deleted_at IS NULL`.
- Pre-restore metadata and blob rows receive the same 48-hour future expiry.
- Once both rows expire, the list omits the recovery point and restore returns
  404. Its content bytes remain physically stored with the expired marker.

The integration test restores a target snapshot, locates the generated
pre-restore row, checks its original bytes, SHA-256 metadata and future expiry,
lists it as verified, and restores it through the authorized restore endpoint
to recover the original file content. A separate test advances the expiry into
the past and verifies the point is no longer visible or retrievable while its
soft-expired blob remains in the database.

## Cleanup boundary

The historical Clojure `delete!` path sends snapshot retention changes through
its `:delete-object` worker, which mirrors the marker to `file_change` and
`file_data`; snapshot creation itself stores both expiry timestamps. The Go
backend has no corresponding task dispatch or physical `file_data` sweeper in
this repository. This change sets the existing logical-expiry fields and
tests the API boundary, but does not claim that expired Go snapshot bytes are
physically purged. A future storage-cleanup task must either connect the
existing shared cleanup worker to these rows or establish an approved cleanup
mechanism; this PR does not add a parallel backup or cleanup service.

No production database or shared environment was used.
