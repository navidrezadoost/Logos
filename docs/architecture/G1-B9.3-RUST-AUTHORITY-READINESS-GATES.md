## 1. Compatibility analyzer and corpus

`logos-app/src/document-core/compatibility-analyzer.ts` is a synchronous, read-only wrapper around the current React candidate adapter and the existing Rust document validator. It does not repair, normalize, migrate or write anything. It reports stable adapter issues or Rust diagnostics and proves the supported fixture's round trip, identity/membership stability, and semantic equality. It delegates document graph validity to Rust; its only pre-adapter structural check detects a root reachable from more than one page and reports ambiguous ownership. A thrown or malformed Rust response is `ANALYSIS_FAILED`, never mislabeled as an invalid source document.

The harness in `logos-app/src/test-support/g1-b9-3-compatibility-smoke.ts` deep-freezes every generated input and checks that the document store and selected IDs are byte-for-byte unchanged. It invokes the compiled `logos-types` WASM validator for the adapter candidate and records classification plus raw diagnostic codes. Exact classifications are in `logos-app/src/document-core/fixtures/g1-b9-3-compatibility-v1.json`.

## 2. Rust/React operation policy

The complete existing comparison contract remains in [G1-B8](G1-B8-RUST-OPERATION-CONFORMANCE.md); G1-B9.3 does not weaken React checks or change ownership. Operation names do not imply equivalence outside the one-page candidate subset.

| Operation / condition | React policy | Rust candidate | G1-B9.3 readiness and exact mismatch |
|---|---|---|---|
| Create root Frame/Rectangle | Planner validates identity, geometry, page/root membership and supported kind. | `CreateShape(parentId=null,index)` | Narrowly adaptable. Rust precondition diagnostics differ in vocabulary; preserve both raw diagnostics. |
| Insert child Rectangle | Planner verifies parent, same-page membership, index, IDs and supported coordinate basis. | `CreateShape(parentId,index)` | Narrowly adaptable. Rust owns parent graph checks; adapter maps page-space to local only under verified translation ancestry. |
| Rename | React trims and validates the name and rejects locked target/ancestor. | Name-only `UpdateShape` | Narrowly adaptable. React normalization is not duplicated as Rust authority; operation request must carry the accepted React result. |
| Reorder roots/siblings | Exact membership permutation; React enforces lock behavior for affected items. | `ReorderChildren` with expected full order and mutation ID | Narrowly adaptable. Invalid order diagnostic differs (`LOGOS_OPERATION_ROOT_ORDER_MEMBERSHIP_MISMATCH` vs `INVALID_SIBLING_ORDER`). |
| Delete subtree | React checks known page ownership, locked relationships, and dependent references before removal. | `DeleteSubtree` | Narrowly adaptable only for already-qualified graph; Rust reference validation can be stricter. Requires differential vectors for every reference class before authority. |
| Reparent, preserve world position | Same-page, no cycles, lock and containment constraints, supported transform ancestry. | `ReparentShape` plus `UpdateShape` local coordinate sequence | Narrowly adaptable for translation-only ancestry. Transform/pivot semantic gaps are explicit incompatibility. |
| Locked objects | React rejection uses `LOGOS_OPERATION_LOCKED_SHAPE`; lock is represented by the `react-locked` compatibility extension. | Rust checks `react-locked`; rejection uses `OPERATION_PRECONDITION_FAILED` at `/operation/locked`. | Reject semantics are covered for the fixture; diagnostics are not identical and the lock field is not canonical. |
| Cycles | React reports `LOGOS_OPERATION_CYCLE`. | Rust reports `CYCLE`. | Both reject, original diagnostics differ and remain intact. |
| Duplicate IDs | React reports `LOGOS_OPERATION_ID_CONFLICT`. | Rust reports `OPERATION_PRECONDITION_FAILED`. | Both reject; exact mismatch is diagnostic code/path. |
| Invalid membership/order | React rejects before commit with its stable planner diagnostic. | Rust rejects with `INVALID_SIBLING_ORDER` or graph validation code. | Both reject; Rust and React diagnostic vocabularies differ. |
| Page ownership / cross-page | React infers ownership from page roots and rejects ambiguous/cross-page cases. | Rust operation carries explicit page ID and validates that ownership. | Different evidence source; adapter is single-page. No cross-page operation delegation. |
| Frame containment | React/A9 scene projection imposes renderer/geometry constraints; adapter derives frame membership. | Rust validates frame references/membership. | Not interchangeable for arbitrary transforms or clipping/masking. Candidate only when the existing A8/A9 supported contract is met. |
| Extensions / vector / components / tokens | React compatibility path retains supported legacy payloads; unsupported renderings carry diagnostics. | Rust core can preserve unknown candidate extensions, but React adapter rejects unknown fields and unsupported record types. | Adapter losslessness is absent; no delegation. Never strip fields to fit Rust. |
| Generic update/batch update, import/hydration | Existing React APIs/load boundaries. | No complete mapping in this bridge. | Not eligible; hydration/import remains its own atomic load boundary. |

Exact Rust diagnostics are retained rather than rewritten into React diagnostics. The conformance comparison uses the complete projected semantic document, not just operation success. Rejections must preserve document, selection and renderer state.

## 3. Performance qualification plan and provisional budgets

Budgets are predeclared design gates, not established product SLOs. Measurements must report environment, warm-up, fixture size, operation sequence and raw repeated samples. At least 30 measured runs after 5 warm-ups per size are required; report p50, nearest-rank p95 and maximum. Keep separate results for native Rust CPU, React planner/adapter JS, WASM call boundary, browser scheduling, Zustand commit, renderer upload/synchronization, and interaction-to-visible-frame.

| Gate (provisional) | Proposed budget | Measurement required |
|---|---:|---|
| React planning + adapter mapping/serialization + Rust/WASM operation + projection | p95 ≤ 8 ms on small/medium; ≤ 16 ms on large | Browser performance clock; include fixture shape count/depth and identical operation list. |
| Zustand commit and selection reconciliation | p95 ≤ 4 ms | Existing React-owned store action in disposable test state; exclude Rust/WASM stage. |
| Renderer sync + next visible frame | p95 ≤ 50 ms | Production A8/A9 renderer in Chromium; report CPU and frame wait separately, pixel evidence required. |
| Native Rust operation | p95 ≤ 4 ms CPU for large fixture | Criterion/controlled native runner, release build and environment metadata. |

These thresholds are provisional internal gates. They are not based on customer telemetry or a user-approved responsiveness requirement. Existing G1-B9/A10 numbers are historical observations from a different fixture/run and cannot satisfy this benchmark.

Five warm-up calls are discarded; 30 subsequent calls are retained as raw samples. The browser artifact records the user agent, platform, hardware concurrency, viewport and device-pixel ratio.

## 5. Proposed G1-B10 pilot and rollback (design only)

This specification is non-executing. A separate Chief Architect authorization is required after the readiness gaps close.

### Eligible population and operations

The only proposed pilot population is one-page, lower-case UUID document/page/shape identities; complete valid parent/child and root membership; `rect`/`frame`/`group`; supported solid fills and known adapter fields; translation-only verified ancestry; no unknown extension fields; no vectors, components/instances, tokens/plugins, or unsupported fill types. Population is per-document classified at load; any unsupported or ambiguous condition keeps the whole page/document on React ownership. No percentage rollout over real users is proposed without authorized, privacy-safe population measurement.

Proposed operation set is root Frame/Rectangle creation, child Rectangle insertion, rename, root/sibling reorder, subtree deletion, and same-page translation-only reparent. Import, hydration, page creation, generic patches, compatibility operations, cross-page moves, and unsupported data are excluded.

### Atomic evaluation/publication

1. Capture an immutable React snapshot, current page ID, selection, and an authoritative revision token. The present editor does not expose a durable server revision precondition suitable for this step; therefore this is a hard **pilot blocker**.
2. Generate one operation ID and one serialized operation proposal. Rust validates the full input, checks revision and operation preconditions, and returns either a complete immutable next document or stable rejection. No partial state is observable.
3. At the sole commit boundary, compare active workspace/session, page, expected revision and operation ID; commit exactly once. Record operation ID as consumed. Duplicate delivery returns the first result and cannot execute a second time.
4. Reconcile selection with the committed IDs, publish React projection and synchronize the existing A8/A9 renderer from that committed state. Renderer completion does not change document ownership.
5. A Rust rejection leaves document, selection, persistence and renderer unchanged. An ambiguous transport/commit outcome is not retried under a new operation ID and never falls through to React after a possibly committed Rust result.

### Controls, fallback and rollback

- Build-time and runtime flags default OFF; server-side cohort flag only after authorized identity/revision gates. Emit a diagnostic-only dry run first.
- Pre-commit failure may use the existing React planner only if Rust has not committed and the same revision is still current; record one authority path. After an apparent Rust commit, never silently rerun in React.
- Rollback disables new pilot operations, drains/blocks in-flight commits by revision/session fencing, then resumes the existing React path. No schema migration or persisted-format change is allowed in this pilot. Already committed Rust results remain ordinary document state and are not reversed by rollback.
- Audit fields: opaque operation ID, build/schema version, document classification, operation kind, expected/result revision, accepted/rejected/mismatch outcome, stable diagnostic code/path, stage timings, renderer completion/failure. No document content, secrets, user text or raw extension payloads.
- Exit/stop conditions: any semantic mismatch, stale revision accepted, duplicate commit, lost identity/membership, non-atomic reject, cross-page write, unknown-field loss, renderer divergence, p95 budget violation over two qualified runs, or inability to disable safely. Stop and return new operations to React before further investigation.

## 6. Non-mutation and evidence boundaries

The browser harness asserts frozen corpus inputs, byte-identical Zustand document state and unchanged selection. Analyzer has no setter/persistence/renderer dependency. Existing G1-B9 shadow evaluation is separately documented as post-React, read-only, and noncommitting. The new task does not touch Go API/schema/revisions, persistence, production telemetry or renderer ownership. WASM validation is an in-memory test call only.

Final-head evidence must include native workspace, WASM ABI, existing G1-B3/A8/A9/A10 regressions unchanged, new Chromium corpus results, React build/type checks, generated-types check, and the hosted artifact. A green new corpus test alone is not a readiness gate.
