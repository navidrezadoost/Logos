## 1. Revision ownership audit

| Value | Source and owner | Meaning and use | Authority classification |
|---|---|---|---|
| File `revn` | Go `file.revn`; returned by create/read. `update-file` locks the file row, records a history row, increments `revn`, then commits. | Change-history sequence. An incoming lower `revn` may be OT-rebased if complete history exists; only a value greater than current is rejected. It is **not compare-and-swap**. Successful update response returns the old `revn`, not the new one. | Canonical server value when read from an authoritative response. It is not a local editor counter. |
| File `vern` | Go `file.vern`; sent on update and compared for equality under the file-row lock. Snapshot restore replaces `data` and increments `vern`, while leaving `revn` at the snapshot's historical value. | Restore/version fence. Prevents an update based on the pre-restore version from silently writing over a restore. | Canonical server value when read from an authoritative response. Distinct from `revn`. |
| Workspace generation | `beginWorkspaceSession()` increments a process-local counter for every route/open attempt. A→B→A receives three generations. | Rejects async work from an old workspace attempt, even when the document ID returns to the same value. | Local guard only. Not persisted and not a server revision. |
| Document-store state | Zustand `documentStore` owns current React pages, shapes and current page; hierarchy actions commit in-process. | Live editor projection and existing mutation authority. The store has no canonical server revision field or coordinated op-commit fence. | Local semantic snapshot. |
| Offline snapshot | IndexedDB `snapshots` stores document identity and a React-shaped snapshot. | Recovery of local document data. It does not record authoritative `revn`/`vern`. | Local persistence; not server evidence. |
| Offline pending-op identity | IndexedDB `pending-ops` uses an auto-increment local `opId` and `localClock`; `SyncManager` reads operations and calls an injected `sendOp` with a rebased patch. | Local queue ordering and deletion after a successful send callback. It does not send a stable operation identity in the observed `sendOp` signature, and its order key is not a canonical revision. | Local diagnostic/order metadata; not server idempotency. |
| Shadow generation | `rust-shadow-evaluation.ts` maintains a runtime generation and compares captured pages/shapes/page ID before read-only evaluation. | Discards stale shadow results. Rust shadow work occurs after React commits and cannot publish a candidate. | Local shadow-evaluation guard only. |
| Rust operation input | `DocumentOperation` and `apply_operation` validate/evaluate graph operations over a supplied document. The WASM ABI returns a candidate or diagnostics without retaining or committing it. | Semantic candidate evaluation. No workspace generation, canonical server revision, or durable op ID is part of this API. | Candidate semantics only; no persistence authority. |

### Go behavior verified from source and existing disposable tests

- `update-file` performs `SELECT ... FOR UPDATE`, then compares incoming `vern` for exact equality. It rejects incoming `revn > current`; for `base-revn < current`, it loads the full intervening history and may rebase and accept the operation. The file update and change row are committed in one transaction.
- An update response contains `{revn: old-revn, lagged}` and no operation ID, resulting revision, or idempotency result. A repeated request after an ambiguous transport failure can therefore append another update. There is no evidence that request retries are deduplicated.
- Restore locks the file and transactionally writes snapshot data, increments `vern`, and leaves `revn` unchanged. A client that fences on `revn` alone can miss a restore.
- The browser's `sendOp` adapter is injected; the inspected `SyncManager` does not itself attach `revn`, `vern`, or its IndexedDB `opId` to that call. Pending operations are processed in IndexedDB retrieval order, then deleted after the callback resolves. No persisted rebase cursor or durable operation-ack protocol is established here.
- Existing Go tests include disposable PostgreSQL coverage for future-`revn` rejection, stale-`vern` rejection, stale-base OT rebase, and revision persistence (`TestUpdateFileHandlerRevisionPersistenceIntegration`), plus snapshot restore incrementing `vern` while preserving historical `revn`. They do not establish idempotency after ambiguous transport outcomes.

## 2. Versioned client precondition envelope

The disposable contract is represented by `RevisionOperationEnvelope<Payload>` in [revision-commit-coordinator.ts](../../logos-app/src/document-core/revision-commit-coordinator.ts). Required fields:

| Field | Classification | Rule |
|---|---|---|
| `contractVersion` | Protocol metadata | Must be an explicitly supported envelope version. |
| `canonicalDocumentId` | Canonical identity from server response | Must match the immutable snapshot. Offline/legacy IDs cannot be promoted by inference. |
| `pageId` | Local semantic address | Must match the captured and current page immediately before local publication. |
| `workspaceGeneration` | Local async guard | Must match the captured session generation at evaluation and publication. |
| `expectedCanonicalRevision` (`revn`) | Canonical server precondition | Required only when loaded from an authoritative version-bearing response; never synthesized from a local clock. |
| `expectedCanonicalVersion` (`vern`) | Canonical restore epoch | Separate from `revn`; required for this Go update contract and must also come from an authoritative response. |
| `localSnapshotGeneration` | Local guard | Must match the exact immutable candidate base and still-current store immediately before publication. |
| `operationId` | Client-generated identity | Unique per logical operation. A client ID alone creates no server idempotency. |
| `operationKind`, `payload` | Typed operation request | Evaluated by the existing Rust candidate ABI and checked against the complete React projection. |
| `candidateSchemaVersion` | Compatibility metadata | Must match `logos-types::document::DOCUMENT_SCHEMA_VERSION` (currently numeric `1`); unsupported versions reject. |

An operation is ineligible for any proposed production Rust authority if either server revision value, document identity, workspace generation, or local snapshot generation is missing or ambiguous. Envelope metadata is not permission to mutate; the server remains authoritative for authorization and persistence.

## 3. Disposable single-owner protocol

The unintegrated coordinator is a conformance model only; the production editor does not import it.

1. Capture a deep immutable document snapshot, page, selection, document identity, workspace generation, local snapshot generation, `revn`, `vern`, and operation ID.
2. Reject missing/ambiguous canonical identity or server revisions before invoking the evaluator.
3. Evaluate the typed payload through the Rust candidate ABI. Rust returns a complete candidate or stable diagnostics; it does not commit.
4. Validate the complete candidate and the React projection. Any invalid graph, mismatched projection, exception, or Rust rejection leaves document and selection untouched.
5. Recheck identity, page, workspace generation, local snapshot generation, `revn`, and `vern` immediately before local publication. One owner publishes one immutable result and increments only the local generation.
6. Reconcile selection only after accepted local publication. The existing renderer receives the committed React projection only. Renderer failure is a post-publication renderer status and cannot be reported as a rejected document operation.
7. The coordinator retains operation IDs only in its own in-memory instance. Same-ID/same-payload pending deliveries share one result; same ID with different payload is rejected; post-completion redelivery is rejected. Closing/recreating the coordinator loses this table. It is **not durable exactly-once**.

This local model does not send operations to Go. A production two-phase protocol cannot be safely completed from the present server response: Go can accept/rebase the change, commit it, and lose the response without returning an operation-keyed result. A client retry may append the same logical intent again. The model therefore cannot establish end-to-end exactly-once publication or a safe React fallback after an ambiguous server outcome.

## 5. Retry, idempotency, and rollback matrix

| Outcome | Current server proof | Required client behavior | Status |
|---|---|---|---|
| Explicit `vern-conflict` / `revn-conflict` response | `vern` mismatch and future `revn` reject before transaction commit. | Reload authoritative file/version; re-evaluate from a fresh candidate; do not replay stale candidate. | Conflict behavior exists; coordinator integration not implemented. |
| Stale lower `revn` with complete history | Go OT-rebases and can commit it. | Must treat server result as a new canonical state and reconcile before a dependent candidate. | Not a compare-and-swap guarantee. |
| Transport fails before request is known to reach server | No request-state proof from current protocol. | Retry only after classifying transport failure as definitely pre-commit; current API does not provide a universal classification. | Unverified. |
| Response lost after server commit | Server response lacks operation ID/result revision; no durable dedup key. | Stop dependent writes; reload canonical state and reconcile; do not issue a new op ID or silently run React fallback. | **BLOCKED**. |
| Offline queue replay | Local queue is replayed serially against fetched state; send callback gets a patch, not a canonical fence/idempotency envelope. | Do not route to Rust authority; preserve queue and require explicit rebase/reconciliation before any future pilot. | **BLOCKED** for Rust-authoritative pilot. |
| Snapshot restore | Atomic restore increments `vern`, leaves `revn` unchanged. | Discard work captured at prior `vern` and reload. | `vern` must be included in future fencing. |
| Renderer failure after accepted local publication | Renderer sync is a separate existing stage. | Keep semantic state once, expose renderer recovery diagnostics; do not apply operation twice. | Local disposable coordinator only. |
| Rollback | No Rust production mutation has been enabled. | Keep current React owner; discard only uncommitted candidates. Any future server commit must reconcile by authoritative read, never reverse by guessing. | No production rollback exercised or authorized. |
