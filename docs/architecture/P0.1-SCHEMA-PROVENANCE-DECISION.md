# P0.1 Track B — Schema Provenance and Disposable Integration Evidence

**Status:** Candidate historical bootstrap executed in an isolated database; canonical schema decision remains open
**Baseline:** `8f27fdfe4fe40a8787cff8d9a20cacde452088ec`
**Historical candidate:** `665bb1ef13c3eeff2e84bf6e0d588a6bdecc6a92`
**Scope:** source lineage, disposable PostgreSQL execution, Go integration compatibility, and one added revision integration test. No deployed or user database was accessed.

## Decision

The removed Clojure migration runner is the only complete checked-in schema history found in Git. Its explicit runner order includes 151 steps: 149 SQL resources and two Clojure transformations. We ran this exact runner against a newly created, ephemeral PostgreSQL 16.14 database and then applied the current Go migration `0001_project_description_photo.sql`. This establishes a **reproducible candidate schema for focused compatibility testing**, not proof that this is the currently deployed/canonical production schema or authorization to use the chain for future installations.

**Recommendation:** have the schema owner certify whether this exact historical runner/step sequence is the authoritative lineage for supported Go deployments. Until then, call it `historical-candidate-151`, not `canonical`. Do not publish it as the Go fresh-install path, execute it against existing deployments, or close P0/M0/M1.

## Provenance and migration semantics

- Current `backend-go/migrations/` contains only `0001_project_description_photo.sql`, an additive `ALTER TABLE` against pre-existing `project` and `storage_object`. `backend-go/cmd/server` connects to a database; it contains no `-migrate` command or bootstrap runner. Top-level README `go run ./cmd/server -migrate` advice is not implemented.
- At the historical snapshot, `backend/src/app/migrations.clj` declares the step order explicitly; `backend/src/app/util/migrations.clj` creates a `migrations(module, step, created_at)` table and records step names. There are no checksums. Duplicate numeric prefixes exist, so sorting SQL filenames is not equivalent to the runner.
- The two non-SQL steps are not optional SQL gaps: **0023** decodes legacy file blobs, migrates page rows into the file’s pages/pages-index data, then drops the old `page` table; **0145** rewrites stored plugin URLs in Transit-encoded profile props. Replaying SQL only would omit these semantics.
- The historical sequence is destructive for data as well as schema (including dropping old tables/columns). Its success on an empty DB cannot establish safety for an existing installation. The current Go handler/schema contracts also differ from the historical Clojure runtime in some areas.
- Existing `docs/r1/PKG-01-SCHEMA-PROVENANCE-FOLLOWUP.md` remains valid: a previous local full-schema clone passed selected Go integration tests, but its origin was not certified. This experiment does not promote that local catalog or the historical chain to canonical status.

## Disposable environment and commands

Created a one-run Docker container from the cached `postgres:16-alpine` image (server reported PostgreSQL **16.14**, image digest `sha256:16bc17c64a573ef34162af9298258d1aec548232985b33ed7b1eac33ba35c229`). The container had no persistent volume and published only `127.0.0.1:55483`. It contains generated integration-test data only. It was not the pre-existing `postgres-container` shown by Docker inventory.

The historical runner was invoked from the detached `665bb1e` source worktree with the explicit order and current host Clojure CLI/Java, using a PostgreSQL JDBC URL that pointed only to this disposable DB. All 151 steps completed, including both Clojure functions. Catalog afterward: 151 migration records and 59 public tables. Running the same runner again produced no migration actions (step-name idempotency). Applying Go migration 0001 succeeded; reapplying it produced `IF NOT EXISTS` notices and succeeded. This was an explicit call to the historical `app.migrations/apply-migrations!` function; it was not a supported Go server command.

**Toolchain qualification:** this proves that the historical code can execute the candidate chain on this host/DB combination. It does not prove reproducibility under the old declared JDK/Clojure toolchain, byte-identical schema, migration checksums, support on another PostgreSQL major, or a supported Go bootstrap command.

### Observed failure / test-harness risk

`TestGetTeamsHandler_Integration` **fails** on the fresh candidate: its profile has `default_team_id IS NULL`; `GetTeamsHandler` ignores the failed scan into a Go `string`, passes `""` as a UUID parameter, and PostgreSQL reports `invalid input syntax for type uuid: ""`. The table and column exist in the historical schema. This is a Go handler/test-fixture behavior defect to review separately, not evidence that the migration runner failed.

The existing asset authorization test’s assertions pass, but its cleanup attempts hit historical deletion-protection triggers and a storage-object foreign-key restriction; those cleanup SQL errors appeared in the disposable PostgreSQL log. The DB was used only for this isolated run, and its container was stopped/auto-removed afterward. This means the integration harness is not hermetic on a persistent shared database.

## Backup/restore evidence

The candidate database, containing only synthetic test rows, was dumped with PostgreSQL 16’s matching `pg_dump`, then restored into a second database in the same disposable PostgreSQL container with PostgreSQL 16’s `pg_restore`. Restore completed without errors. Dump SHA-256: `5f0d19a68a16521ad14a1a84ac31389b3bfa6956ee4d20d181c69a1f169dd7fe`. Selected row counts matched exactly:

| Table | Source | Restored |
|---|---:|---:|
| migrations | 151 | 151 |
| project | 14 | 14 |
| file | 10 | 10 |
| file_change | 2 | 2 |
| profile | 12 | 12 |
| storage_object | 7 | 7 |

An initial attempt with the host PostgreSQL 18.6 dump/restore client against PostgreSQL 16 emitted unsupported `SET transaction_timeout` on restore; that was discarded as a client/server major mismatch. The matching PostgreSQL 16 client succeeded. This is schema/data dump-and-restore evidence for this candidate and synthetic rows only, not an application backup, disaster-recovery drill, historical upgrade, rollback, or production restore guarantee.

## Remaining gaps and risk register

| Risk | Evidence | Required owner/action |
|---|---|---|
| Historical candidate not certified as deployed source | No migration checksum/version table or authoritative deployed snapshot; previous local catalog provenance is unknown. | Schema/DB owner to identify supported deployed versions and lineage. |
| No Go clean-install path | One additive migration; Go server has no migration flag/runner. | Approve a canonical bootstrap/upgrader only after lineage and non-SQL semantics are reviewed. |
| No rollback test | Historical chain has destructive steps and no demonstrated down migration. | Define forward recovery/backup/restore policy; do not promise rollback. |
| GetTeams null default-team failure | Reproduced against fresh candidate. | Backend owner to decide correct anonymous/no-default-team contract and add a regression test in a separate code change. |
| Legacy change encodings | Go writes JSON changes; old Transit+zstd rows are skipped during competing-change loading; missing/undecodable history does not fail closed. | Domain/backend owner to define compatible decoder/migration or explicit conflict/recovery response. |
| Asset test cleanup | Deletion-protection/FK cleanup errors in existing test. | QA/backend to make test cleanup isolated/transactional and validate all asset lifecycle/storage adapters. |
| Production equivalence | None of these runs used a deployed or copied user DB. | Do not apply candidate migrations to any existing/user/production DB without a separate approved compatibility and backup plan. |

**Track B outcome:** historical chain is an empirically executable candidate and the listed Go project/file/share/asset/revision flows mostly pass on it. Canonical schema and fresh-install approval remain **OPEN**; rollback/restore and all Go handlers are not certified.
